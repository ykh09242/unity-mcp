# Input discovery and local log buffering

Exact path targets enumerate loaded normal scene roots and the persistent Play Mode scene. They preserve duplicate-name errors and reject inactive targets, assets and preview scenes. The Editor persistent-scene binding is cached; versions without that binding retain a compatibility inventory fallback. No temporary scene object is created to discover the persistent scene.

The uGUI recorder uses scene-root component queries and reusable lists. Hierarchy changes request a scan, coalesced to at most four per second; a two-second reconciliation also discovers changes for which Unity sends no hierarchy notification. Initial recording and scene-load scans remain immediate. Dynamic buttons may therefore wait up to two seconds before observation starts. The existing 512-button limit and component cleanup remain in force. Preview scenes are excluded.

`manage_input status` reports `active_input_handling`, raw simulation flags and `input_observation`. Old Input Handling supports the existing target-based uGUI event dispatch and a read-only `UnityEngine.Input` recorder. New and Both retain the Input System recorder and virtual-device backend. Direct uGUI dispatch does not change `UnityEngine.Input`; Input System virtual devices also do not change legacy reads in Both mode. No backend changes Active Input Handling, focuses windows, sends OS input or changes background settings.

The Old-mode recorder samples observed key edges, the first three mouse buttons, pointer movement, wheel values and up to ten touch contacts in game `Update`. It starts a private frame pump only for the recording session and removes it on disposal; inactive recording does not poll input. Idle frames do not enumerate keyboard candidates. Keys or touches already held when recording starts do not become invented presses. Legacy wheel units are preserved. Touch-to-mouse emulation can make mouse provenance ambiguous, so mouse samples coincident with emulated touches are omitted with a diagnostic. Input Manager axes/buttons, joystick mappings and IME text are not inferred. Physical input remains subject to Unity's existing focus/background policy.

Recording status preserves `input_observation.backend`, `source`, `frame_clock`, per-device observation flags and `raw_replay_available`. Legacy drafts carry the `recorded-legacy-input` tag after saving. Unity exposes legacy key and pointer reads but no public general raw-state injection API; these recorded raw steps cannot replay into `UnityEngine.Input`. For a uGUI flow, retain the observed target-based `click_ui` steps and remove overlapping raw pointer steps during review. Legacy target clicks are retained alongside raw observations with an explicit duplication warning. Cross-backend raw replay requires an Input System consumer and review of timing, key layout and wheel scaling. The draft flag remains set until the author reviews it.

Recording names are saved-file slugs: 1-64 lowercase ASCII letters/digits, hyphens or underscores, beginning with a letter/digit (`^[a-z0-9][a-z0-9_-]{0,63}$`), for example `menu-flow-01`. Use descriptive text in the scenario's steps; spaces, uppercase letters and localized recording filenames are not accepted.

Legacy API references: [Input.GetKeyDown and game Update](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/Input.GetKeyDown.html), [read-only mouseScrollDelta](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/Input-mouseScrollDelta.html), [input handling symbols](https://docs.unity3d.com/6000.3/Documentation/Manual/scripting-symbol-reference.html), and [Unity's legacy Input bindings](https://github.com/Unity-Technologies/UnityCsReference/blob/6000.0/Modules/InputLegacy/Input.bindings.cs). The internal Editor-only touch simulation binding is not a supported public keyboard/mouse/gamepad injection backend.

Opt-in local logging records bounded execution metadata only. Synchronous and asynchronous results use the same scalar success/error classification; payloads, action strings and exception text are not retained or reparsed for logging. Unavailable outcome metadata is recorded as UNKNOWN. The wire response envelope is unchanged.

A background writer owns log handles and rotation. Producers only enqueue records. The queue holds at most 1024 records, each at most 16384 characters; one worker can hold another 64 records while writing. When full, new entries are dropped. Subsequent metadata rows include cumulative dropped and failed counts, and the logging toggle tooltip reports the current counters when Advanced settings refresh. A failed count covers rows in a batch that encountered a write failure, including any partially written batch.

The writer coalesces records for at most 100ms (explicit flush and shutdown bypass this delay), flushes batches, retains one previous file per log, and limits each ordinary log segment to 1 MiB. Reload and Editor quit request queue drainage with a two-second wait; a blocked disk or process crash can still lose pending diagnostics. Logging failure does not fail tools or recursively write Unity logs. Explicit Flush waits for all records accepted before the call, reports timeout or prior write failure, and does not treat previously rejected records as accepted. Readers of live logs should use shared read/write file access. Existing files named mcp.log.1 and mcpError.log.1 are reserved for rotation; unrelated files are preserved.
